## 1. What this project is

A local, browser-based tool that turns a QA engineer's **feature selections** into a complete,
schema-valid suite of **test cases for the NextBillion.ai Route Optimization API**
(`POST /optimization/v2`).

The design principle in one line:

| Layer | Owns |
|---|---|
| **Compiler** | *All* product truth — every field, constraint, business rule |
| **Claude** | The *reasoning* — which scenarios and values to test |
| **The app** | *Validation* — every generated payload checked against the real schema + rules |

**Scope is locked to authoring.** The tool does **not** execute test cases against the live API and
does **not** call Claude automatically. Generation is copy-prompt → paste-result. Execution happens
on a separate platform. Do not add execution features without an explicit decision from the owner.

**Test types are exactly two:** Positive and Negative. Boundary / invalid / infeasible scenarios are
authored *within* those two, never as separate categories.

## 4. The 5-step user flow

1. **Scenario** — Region, vehicle count, job count, test types (Positive / Negative), and a single
   **Number of test cases**. That number is a **ceiling**, not a target — the planner derives
   everything else and may generate fewer (see §5.2).
2. **Features** — checkbox tree built **live from `openapi.json`** at page load. Ticking a parent
   ticks all descendants. Enum leaves expand into one checkbox per allowed value (path encoded as
   `field=value`). Draft overlay fields show an amber `draft — not in spec` chip. Every *selected*
   row shows a **role pill** — `target` (gets dedicated cases) or `support` (injected into bodies)
   — which is clickable to flip that field's role for the run.
3. **Copy Claude prompt** — assembles skills + API facts + scenario + coordinates + compiled
   knowledge + the supporting-fields block + the allocation. Buttons: Copy / Preview / Maximize.
4. **Paste into Claude**, then load the returned JSON array back (file loader preferred over paste —
   pasting large JSON from a chat drops characters; the loader also repairs control chars).
5. **Validate & Render** — AJV + business rules per case, 10-column table, coverage matrix, CSV export.


The 2.4 MB spec is **never** sent — only the compiled knowledge for selected features.

### 5.2 Roles and the allocation planner (`buildPlan`)

**One axis, not two.** The old `standard` / `important` weighting is gone. A selected field has a
**role**, resolved as: user's pill toggle → `fieldRoles` in `coverage-config.json` → `target`.

- **target** — a test subject; receives dedicated cases.
- **support** — injected into request bodies as realistic context; never a subject. Paths with no
  countable unit (`id`, `description`, `locations.*`) are always support — previously they were
  silently dropped and did nothing.

**Weight comes from the compiled obligations**, not from a knob. `unitOf()` collapses paths into
units (`vehicles.capacity`, `options.routing`, `relations`); a unit's weight and cap both equal its
summed positive + negative obligations.

**`N` is a ceiling, not a target.** The planner produces the largest suite ≤ N that stays fully
backed by authored coverage aspects. Generating fewer than N is normal and correct — nothing is ever
invented to reach the number.

**The Positive/Negative ratio is a global rule**, not per-feature: `ratio.positiveShare` in
`coverage-config.json` (0.9 = 90/10). Per-unit obligation ratios no longer decide the split, because
rounding across units cannot hold a suite-level ratio.

The planner:

1. Group selected paths by role; a unit is a target if any of its selected paths is a target.
2. **Fallback** — if there are no targets, promote the supporting fields to subjects (flagged
   `promoted` in the readout) so a selection can never produce an empty plan.
3. **Capacity** — `posCapacity` / `negCapacity` = Σ positive / negative obligations over target units.
4. **Size the suite once**, so the ratio always holds:
   `sized = min(N, ⌊posCapacity / 0.9⌋, ⌊negCapacity / 0.1⌋)`, then
   `positive = round(sized × 0.9)`, `negative = sized − positive`.
   Capping the two halves *independently* would let the negative half keep filling after positive
   aspects run out and silently skew the suite — an actual bug caught in testing.
   **When only one test type is ticked** the ratio does not apply: that type takes `min(N, capacity)`
   and the other is zero.
5. **Combination cases** — `⌊effective × combinationShare⌋` (0.15), capped at the target-pair count
   and at the positive half. Funded from **inside** the positive share, not reserved on top. Sized
   off the *actual* suite, not the requested N — otherwise a large N lets combinations consume the
   whole positive half and starve per-feature coverage.
6. **Distribute each half separately** across targets via largest-remainder, proportional to that
   half's obligations, so both sum exactly. Units that get nothing are reported in `dropped` — never
   silently truncated.

Deterministic throughout: no `Math.random`, ties break by index, so the same selection always
produces the same plan.

*Worked examples (verified 2026-07-28 by executing the real `buildPlan` against the compiled KB):*

| Selection | N | Result |
|---|---|---|
| `relations` + `capacity` + `time_windows` (7P/8N available) | 40 | **7** cases — 6P/1N (5 per-feature + 1 combination) |
| 8 features (16P/13N available) | 40 | **17** cases — 15P/2N (13 per-feature + 2 combination) |
| same 8 features | 200 | **17** — unchanged; the KB, not N, is the limit |
| same 8 features, Positive only | 40 | **16** cases — 16P/0N |

The suite lands at 86–90% positive; small suites can't express 90/10 exactly with whole cases.
Note that **positive aspects are usually the binding constraint** — the KB is ~63% positive while the
rule demands 90%, so narrow selections yield noticeably fewer cases than N.

### 5.2.1 What is no longer generated

Removing the reserve means **global negatives** (auth / schema / error / constraint) are no longer
produced — no feature's obligations fund them, and the 10% negative budget is consumed entirely by
per-feature negatives. `globalSuites` remains in `coverage-config.json` for a future dedicated pass.
This is a deliberate, accepted coverage loss.

### 5.3 Validation (`validateOne`)

- AJV 2020 compiled against a **sanitized** copy of the request schema: `enum`, `x-enum-options`,
  `examples`, `example`, `default`, `format`, `$schema` are stripped, because this spec's enum values
  are backtick-wrapped documentation artifacts (`` "`duration`" ``) that would false-fail everything.
  Structure / types / required / `additionalProperties` are kept — those catch the real defects.
  Correct enum values still reach Claude through the prompt.
- Plus `businessRules(body)`: `location_index` in range for vehicles/jobs/shipments,
  `vehicles` present and non-empty, at least one of `jobs` / `shipments`.

Badges: `✅ valid` · `❌ invalid` (positive with errors) · `⚠ invalid (intended)` (negative with
errors — expected for malformed negatives) · `✔ valid (infeasible-type)` (negative that parses
clean — the 200 + `result.unassigned` kind) · `n/a (no body)` (string `testData`).

### 5.4 Dedup & add-more

`fingerprintBody` builds an order-independent structural hash (top-level keys, array counts, first
vehicle/job field-set, canonicalized `options`) — *not* byte equality, so re-rolled coordinates don't
look like new tests. `caseKey = type|feature|fingerprint`. Loading prior suites into the
**"Add more to an existing suite"** panel makes the prompt emit only new cases, continues ID
numbering per category, and flags duplicates on render.

### 5.5 Output contract (what Claude must return)

A bare JSON array; each element has exactly these keys:

```json
{ "testCaseId": "TC-RO-POS-001", "feature": "...", "title": "...", "description": "...",
  "testData": { }, "details": { "features": ["vehicles.capacity"], "archetype": "positive" },
  "expectedResult": "...", "priority": "P2", "type": "Positive" }
```

IDs are `TC-RO-POS-###` / `TC-RO-NEG-###`. The render table's 10 columns are
*Test Case ID · Feature · Title · Description · Test Data · Details · Expected Result · Priority ·
Type · Validation*; "Details" counts are computed from `testData`, not trusted from the model.

### 5.6 Coverage matrix

Rows are **test subjects only**. Supporting fields are listed below the table in a neutral
`support — injected into request bodies, not scored` state and excluded from the percentage — they
are injected by design, so scoring them as uncovered would permanently depress the number. An
archetype column shows `—` when that test type isn't selected, rather than a false gap.

## 6. `compile.mjs` — the compiler

Reads `openapi.json` + `enrichment/*.json` + `rules/*.json`, and:

1. Walks the request schema and emits a structural record for **every** path (213).
2. Merges enrichment onto it — **hard-fails** if an enrichment file's `path` doesn't resolve in the
   spec (orphan). `--lenient` downgrades that to a drift entry.
3. Parks any file with `"status": "proposed"` — **never embedded** until a human ratifies it by
   deleting the `status` field. This is the "AI drafts, human ratifies" gate.
4. Computes **coverage obligations** per feature by classifying each `testingGuidance` bullet:
   `Positive:` / `Boundary:` → positive; `Negative-validation:` → 4xx at submit;
   `Negative-infeasible:` → 200 + unassigned or 422; `Interaction:` → combination cases.
   Untagged bullets fall back to keyword inference.
5. Builds the graph: edges from `related`, hyperedges from each rule's `applies_to`, then union-find
   clusters (size ≥ 2).
6. Emits `data/compiled/` + a spec-hash snapshot used next run to flag `needsReview` paths whose
   spec node changed under existing enrichment.

**Enrichment file shape** (see `enrichment/vehicles.capacity.json` as the model):
`path`, `summary`, `range`, `constraints[]`, `businessRules[]`, `validationRules[]`,
`testingGuidance[]`, `related[]`, `rules[]`, `_source`.

**Rule file shape** (see `rules/skills-superset.json`): `id`, `summary`, `applies_to[]`, `rule`,
`testingGuidance[]`.

## 9. Draft-feature overlay & review workflow

`overlay.json` lets the tool author test cases for features that ship **before** the spec catches up.
Currently two entries: **`split-order`** (`jobs.split` with `can_be_split`, `max_splits`, `quant`) and
**`unused-vehicle-reasons`** (`options.report_unused_vehicle_reason`), each distilled from their source spec docs.

**Key insight: Draft features have a different guidance flow than spec features.**

| Layer | Spec features (in openapi.json) | Draft features (in overlay.json) |
|---|---|---|
| **Guidance source** | `enrichment/*.json` files (compiler reads) | `overlay.json` metadata (app reads at runtime) |
| **Enrichment files** | ✓ Required — compiler merges onto compiled KB | ✗ Not used — guidance is in overlay.json |
| **Flow** | `enrichment/*` → `compile.mjs` → `data/compiled/` → app reads | `overlay.json` → app runtime merge → feature tree + prompt |
| **Why different** | Compiler processes offline; needs all facts as files | Overlay is client-side only; metadata is self-contained |

**Correct workflow for adding a draft feature:**

1. **Add overlay.json entry** with: `id`, `status: "draft"`, `target` (ends with `.properties`), `title`, `fields` (schema definition), `constraints`, `testingSuggestions`, `limitations`
   - Example target paths: `"jobs.items.properties"`, `"options.properties"`, `"relations.properties"`
   - ✓ Include responseFields for documentation (not validated, informational only)
   - ✗ Do NOT create enrichment/*.json files for draft fields
   - ✗ Do NOT create rules/*.json files for draft constraints (put them in overlay `constraints`)

2. **Verify compilation** runs cleanly: `node compile.mjs` (should report 0 orphans)

3. **Test in app**: Refresh page, draft field appears in tree with amber chip + full guidance from overlay

4. **When feature lands in openapi.json**: 
   - Add to real spec
   - Create `enrichment/*.json` files for the new paths (containing testingGuidance, businessRules, etc.)
   - Delete overlay.json entry
   - Run `compile.mjs` (embedds guidance into compiled KB)

**Current draft features:**
- `split-order` — `jobs.split.{can_be_split, max_splits, quant}` (from Split Order PDF)
- `unused-vehicle-reasons` — `options.report_unused_vehicle_reason` (from Unassigned Reasons doc)

**Details:** See `DRAFT_FEATURES_REVIEW_GUIDE.md` (how to review), `DRAFT_FEATURES_WORKFLOW.md` (comprehensive guide), and `DRAFT_FEATURES_PROCESS.md` (step-by-step) — **note:** those guides still reference enrichment files; use the corrected workflow above instead.

## 10. Known gaps / discrepancies (verified 2026-08-02)

These are real facts about the current tree — don't be surprised by them, and fix them deliberately.

1. **`TOOL_SPECIFICATION.md` field count.** Its compiled state table says 167 enriched where the compiler reports 168 — the extra is `relations.steps.id`, enriched but out of scope by the `id`-leaf rule. Coverage is genuinely complete either way.
2. **Enrichment depth is uneven** despite "0 gaps", and this now directly limits how many test cases
   a selection can produce. `drift-report.json → coverageLint`: **72** features have no Negative
   obligation, **8** have no Positive obligation, **87** have empty `validationRules`. Those features
   contribute little capacity, so the planner caps low on them — deepening enrichment is the way to
   raise the ceiling.
3. **Cross-field rule coverage: tracked but not fixed.** `drift-report.json → coverageLint.unbackedRelated` lists **77** enriched paths with a non-empty `related[]` but no rule reference — real relationships identified during enrichment but not yet formalized as rules. The compiler now tracks this backlog (previously invisible) via `staleRuleRefs` (must be 0 after each work session) and `unbackedRelated` (not a gate, but a visible priority queue for future rule authoring). No structural change; same obligations/coverage calculations apply.
4. **`fieldRoles` in `coverage-config.json` is a curated first pass.** It covers the obvious
   scaffolding (ids, descriptions, `locations.*`, index/service/setup leaves). Any field not listed
   defaults to `target`. Deliberately conservative: marking a constraint-bearing field as support
   would silently remove its dedicated coverage. Long-term this should migrate into `enrichment/`
   as an authored `role` field — the config lives as data so that move needs no code change.
5. **Role overrides are per-session.** The pill toggles live in an in-memory `Map` and reset on
   reload (and on **Clear**). Deliberate — a run's roles are part of that run's intent, not
   persistent state — but worth knowing before a long session.
6. **Only one region.** `REGIONS = ["USA"]` and `data/locations/USA.json`. Adding a region = drop in
   `data/locations/<Region>.json` + add the name to that array.
7. **No git.** No version history — no safety net for destructive edits.
8. **`enrichment.zip`** is a stale 2026-07-20 snapshot, unused at runtime.
9. **Aspirational vs. actual:** `QA_Authoring_Studio_Architecture_Review.md` describes a
   React + Fastify + SQLite server variant that **does not exist**. The real tool is the static page.
   Read that document as a roadmap, not as a description of the code.

## 11. Conventions to follow when changing this project

- **Product facts go in `enrichment/` or `rules/` — never in `app.js`, never in `skills/`.**
  (The one deliberate exception is the short `# API facts` block hardcoded in `buildPrompt`.)
  Curated *policy* that isn't a product fact — like `fieldRoles` — belongs in `coverage-config.json`,
  not as a JS constant.
- **Never hand-edit `data/compiled/`** — it is generated. Change the inputs, then run `compile.mjs`.
- **AI-drafted enrichment lands as `"status": "proposed"`** and stays out of the compiled output
  until a human deletes that field. Preserve that gate.
- **Determinism:** no `Math.random()` / `Date.now()` in generation paths — `sampleCoords` uses a
  fixed multiplier, allocation ties break by index, and CSV filenames derive from the scenario. Keep
  it that way so a selection reproduces the same plan.
- **Never pad a plan beyond authored depth.** If the user asks for more cases than the selection's
  obligations support, cap and report it. Padding forces Claude to invent facts, which breaks the
  Knowledge-Fidelity Contract in `skills/_base/SKILL.md`.
- **Never truncate coverage silently.** A feature that gets no cases must appear in `dropped` and be
  named in the readout.
- **Spec updates:** replace `qa-studio/openapi.json` (and the `Knowledge/` copy — keep them
  identical), reload the page, then `node compile.mjs` and read `drift-report.json → needsReview`.
- **Skill edits go in `skills/`,** not `FALLBACK_CONTRACT`.
- `index.html` imports `app.js` with a `?_=Date.now()` cache-bust, so a plain reload picks up edits.
